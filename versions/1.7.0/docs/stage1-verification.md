# Исторический протокол этапа 1 · RG-1D 1.3

**Этот документ фиксирует промежуточное состояние этапа 1. Последующие этапы уже реализованы в 1.6.0; актуальные функции и итоговые проверки — [verification.md](verification.md). Формулировки ниже «не опубликовано / следующие этапы» относятся к моменту промежуточной проверки, не к текущему статусу релиза.**

Дата: 20.11.2026. Автор приложения: Apdulium-beep. Релиз не опубликован; указатель текущей версии и прежний ярлык остаются на 1.5.0. Второй режим по методике отложен, формулы не подбирались под эталон.

## Изменения

- `src/RiverGuard.Core/Solver.cs`: поддерживаемый бытовой приток, отдельное установление режима, единый снимок для двух расчётов, баланс с бытовым притоком, согласованные времена фронта/гребня/спада и сохранение фоновых историй. Нет автоматического продления аварии: при незавершённом спаде значение не определено и показано предупреждение.
- `src/RiverGuard.Core/Models.cs`: необязательные опорный уровень объёма, доля длины плотины и отдельное дно НБ; производные параметры не округляются; отдельное время максимума полного уровня и данные установившегося состояния.
- `src/RiverGuard.Core/Geometry.cs`: отдельное дно НБ при наличии, прежнее DamBed как совместимый резерв.
- `src/RiverGuard.Core/SourceDischarge.cs`: альтернативная ширина Eр·Bв; формула напора над порогом не заменялась глубиной от дна.
- `src/RiverGuard.App/MainWindow.xaml`, `MainWindow.Startup.cs`, `MainWindow.xaml.cs`: ввод новых параметров, отображение Hр/W/ширины, фазы вычислений и график реального безаварийного фона. Поля доли скрыты в остальных механизмах.
- `src/RiverGuard.App/ExportService.cs`, `ExportService.Formats.cs`: фактически используемые параметры, новый баланс и честное описание метода; отсутствующий гребень выводится как неопределённый, а не 0. Структура нового отчёта относится к этапу 2 и пока не вводилась.
- `src/RiverGuard.Tests/Stage1Checks.cs`, `Program.cs`: регрессии этапа 1 и дополнительные проверки стационарности каждого из 33 примеров.
- `src/RiverGuard.App/MainWindow.Stage1Checks.cs`: проверки русскоязычного ввода/очистки nullable полей, вычисленных значений, сохранения и экспорта; вызываются в изолированном smoke-тесте.
- `src/RiverGuard.App/Controls/OptionalNumberConverter.cs`: пустое необязательное число преобразуется в null; принимаются десятичные запятая/точка без разделителей групп, некорректное значение помечается ошибкой и не заменяет исходное. Исправлено обнаруженное при реальном UI-прогоне поведение стандартного WPF-конвертера, не позволяющего очистить nullable число.
- `src/RiverGuard.App/RiverGuard.App.csproj`, `version.json`, README, RELEASE_NOTES, docs/model.md: номер рабочей версии и описание изменений. SchemaVersion остаётся 1; старые поля не переименованы, новые поля необязательны. Третьесторонние лицензии сохранены.

## Проверки и воспроизведение

Из корня репозитория:

```powershell
dotnet build versions/1.6.0/src/RiverGuard.sln -c Release
dotnet run --project versions/1.6.0/src/RiverGuard.Tests -c Release --no-build -- --stage1-tests --catalog-tests --stage1-report artifacts/stage1-1.6.0-results.json --catalog-report artifacts/stage1-1.6.0-catalog.json
dotnet publish versions/1.6.0/src/RiverGuard.App -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -o versions/1.6.0/app
versions/1.6.0/app/RiverGuard.exe --smoke-test
```

Сводки численных запусков находятся в `artifacts/stage1-1.6.0-results.json` и `artifacts/stage1-1.6.0-catalog.json`; копии сводок сохранены также в `docs/stage1-results.json` и `docs/stage1-catalog.json`. Результаты UI — `app/SmokeTest/*checks.txt` и датированный `success.txt`. Это синтетические проверки, личные проекты не используются.

Численный итог: **383 PASS, 0 FAIL** — все прежние 255 проверок и 128 дополнительных (62 проверки этапа 1 и 66 проверок стационарности каталога). Предметные проверки включают рост Q/V/H при подъёме уровня, инвариантность высотного нуля, закрытый источник, упорядоченность событий, баланс с бытовым притоком, связь уровня/объёма, долю длины плотины и совместимость проекта. Проверки приложения: прежние 87, обновление 47 и новые 19 проверки этапа 1 — **153 PASS**. Сборка решения: **0 предупреждений, 0 ошибок**. Self-contained Windows x64 EXE собран и запущен локально; окончательная дата smoke-прогона указана в `success.txt`.

Существующая проверка версии модели для затвора/отверстия осознанно обновлена с RG-1D/1.2 на текущую RG-1D/1.3: прежний номер означал бы неверную маркировку изменившегося расчёта. Физические проверки не удалены и допуски прежних проверок не ослаблены.

В `MainWindow.UpdateChecks.cs` исправлен тестовый набор обновления: следующий номер формируется от версии текущей сборки, а не фиксирован как 1.6.0. Иначе 1.6.0 закономерно отклоняла равную ей тестовую версию как «не более новую». Производственный механизм обновления не менялся; проверки отклонения равной/старой версии сохранены.

## Пример «Три створа»: 71,3 и 72,3 м

Параметры совпадают с двумя предоставленными отчётами; независимый объём 11,6 млн м³, ширина 12 м, прежний резерв дна НБ. Новые опции не включались для этой сверки.

| Створ | Qmax 71,3 / 72,3 м, м³/с | Vmax 71,3 / 72,3 м, м/с | Hmax 71,3 / 72,3 м, м |
|---|---|---|---|
| 1 | 323,011 / 387,939 | 2,144 / 2,497 | 2,936 / 3,159 |
| 2 | 254,367 / 289,256 | 1,118 / 1,221 | 3,778 / 4,010 |
| 3 | 253,960 / 287,506 | 0,832 / 0,905 | 4,559 / 4,790 |

Общий бытовой приток 232,932 м³/с. Выпуск водохранилища: 237 070,883 / 608 845,006 м³. Время установления исходного режима 5,010 модельного часа; конечный остаток 0,025 %. Это не время реального ожидания пользователя и не время после аварии.

При закрытом проране за последующие 3 ч максимальные отклонения глубин: 0,033 / 0,030 / 0,029 %, расходов: 0,006 / 0,010 / 0,025 %. Ранее глубины менялись на 46 / 26 / 18 %, а расход почти исчезал. Новый критерий 1–2 % выполнен для этого примера.

Смена уровня +1 м увеличивает Qmax примерно на 20,101 / 13,716 / 13,209 %, Vmax — на 16,454 / 9,215 / 8,715 %, Hmax — на 7,607 / 6,137 / 5,084 %. Общий перенос абсолютных отметок +1 м не меняет Q/V/H и времена в пределах численного допуска. Уровень ниже порога даёт строго нулевой расход источника.

На исходном 3-часовом горизонте спад не завершён во всех трёх створах и не определяется. Гребни аварийной добавки: 2,523 / 2,645 / 2,770 ч; фронты: 0,061 / 0,102 / 0,213 ч. Перестановка прежних ошибочных времён не использовалась: изменено само определение событий на согласованное.

При проверке пологого участка и большой шероховатости понадобились 121,732 и 100,196 модельного часа; поэтому лимит разгона 48 ч оказался недостаточным и увеличен до 7 суток без ослабления критериев. При нулевом бытовом притоке выбран гидростатический начальный режим с сохранением объёма. Это явно описанный выбор безаварийного состояния, не модель естественного опорожнения участка.

## Ограничения и следующие решения

- Чистые Windows 10/11 без SDK/Office и без прав администратора не испытаны. Проверяется локальная self-contained сборка на компьютере разработки.
- Независимая натурная/лабораторная валидация, полноценная сеточная сходимость и нормативное соответствие не установлены. Пики ячеечных расходов и межъячеечные потоки не тождественны на грубой сетке; постоянство последних при установлении не доказывает точность первых.
- Для условного нулевого створа старого проекта сохраняется дно водохранилища; для реального объекта нужно подтвердить отдельную отметку дна НБ и источник поддерживаемого бытового притока. Пример не является подтверждённой геометрией реального объекта.
- Новые зоны, критерий КР одного часа, полная структура DOCX, Enter-навигация, история запусков и отключение автоматической проверки обновлений по умолчанию остаются следующими этапами.
- Допуск 5 % не принят как подгонка RG-1D к другой модели. Для будущего методического режима его можно обсуждать после получения формул; времена около нуля требуют абсолютного допуска.
- Перед этапом 2 требуется решение по ВКЗМ (1,5 м или сочетание 1,0 м и 0,7 м/с) и по необходимости x86. До этого предлагается оставить прежний сценарный порог 1,5 м, без заявления о нормативности.

Следующий этап выполняется только после подтверждения пользователя. Публикация 1.6.0 сейчас не производится.
